# Split Auth Screen into 3 Scenes: Login, Register, Forgot Password

## Context

The current auth screen (`Assets/Scenes/Login.unity`) is a single flat Canvas showing every
field and button for all three auth flows simultaneously: email, password, child name,
birthdate, doctor code, and Register/Login/Forgot-Password buttons all visible at once,
driven by one script (`Assets/Scripts/Region1/Adventure/UI/AuthScreenController.cs`, 177
lines). There is no tab/panel switching — users are expected to know which subset of fields
applies to which button.

The rest of the game uses one `.unity` scene per screen, transitioning via
`SceneManager.LoadScene` (WorldMap, cutscenes, quest maps, success screens all follow this
pattern). No panel-swap/tab infrastructure exists anywhere in the project. This design splits
the auth screen into three scenes to match that convention and remove the field-coupling.

The scene itself is not hand-authored — it's generated by an idempotent editor tool,
`Assets/Editor/WordFlowLoginSceneBuilder.cs` (`Tools > WordFlow > Build Login Scene`), which
is the effective source of truth for the scene's GameObject layout.

Forgot Password is already a self-contained, backend-free flow
(`AuthSession.SendPasswordReset` → `FirebaseAuthClient.SendPasswordReset`, which calls
Firebase's Identity Toolkit REST API directly). No backend changes are required by this
design — confirmed zero `/register`, `/login`, or `/reset-password` endpoints exist in
`WordFlow-Backend`; auth is handled entirely client-to-Firebase, with the backend only
consulted afterward via `GET /bootstrap`.

## Goals

- Replace the single combined auth screen with three focused scenes: `Login.unity`,
  `Register.unity`, `ForgotPassword.unity`.
- Each scene shows only the fields relevant to its flow.
- Users can navigate between the three via text links (not dead-ends).
- Keep the scene-builder-as-source-of-truth pattern; scenes stay regeneratable, not
  hand-edited YAML.
- No backend changes needed.

## Non-goals

- No changes to `AuthSession`, `FirebaseAuthClient`, or any backend endpoint.
- No new backend "forgot password" endpoint — the existing Firebase-direct flow is reused
  as-is.
- No introduction of a panel/tab system — this design deliberately follows the existing
  one-scene-per-screen convention rather than building new panel infrastructure.

## Design

### 1. Scenes

Three scenes replace the single `Login.unity`:

- **`Login.unity`** (entry point, build index 0, same role as today)
  - Fields: email, password
  - Button: Login
  - Links: "Don't have an account? Register" → `Register.unity`; "Forgot Password?" →
    `ForgotPassword.unity`
  - On `Start()`, attempts silent auto-login via `AuthSession.Instance.TryAutoLogin` if a
    stored refresh token exists (moved unchanged from current `AuthScreenController.Start()`)

- **`Register.unity`**
  - Fields: email, password, child name, birthdate (YYYY-MM-DD), doctor code (optional,
    `WF-XXXX`)
  - Button: Register
  - Link: "Already have an account? Login" → `Login.unity`
  - No auto-login attempt on `Start()`

- **`ForgotPassword.unity`**
  - Field: email only
  - Button: Send Reset
  - Link: "Back to Login" → `Login.unity`
  - No auto-login attempt on `Start()`

All three scenes include an `AuthBootstrap` GameObject (`FirebaseAuthClient` + `AuthSession`
components, `DontDestroyOnLoad`), matching today's setup. This is safe to include in all
three: `AuthSession.Awake()` already self-destructs duplicate instances, so whichever scene
loads first "wins" and the session persists across the new scene boundaries.

### 2. Code structure

- **`AuthControllerBase`** (new, abstract `MonoBehaviour`) — shared across all three
  controllers:
  - Serialized refs: `statusText`, `busyIndicator`
  - `ShowStatus(string message)` — displays status/error text (Thai messages, as today)
  - `SetBusy(bool)` — toggles busy indicator
  - `IsValidEmail(string)` — shared validation helper
  - `GoToScene(string sceneName)` — thin wrapper around `SceneManager.LoadScene`

- **`LoginController : AuthControllerBase`** — email/password fields, Login button handler
  (moved from `AuthScreenController.OnLogin`), auto-login-on-`Start()` (moved from current
  `Start()`), link handlers to Register and Forgot Password scenes.

- **`RegisterController : AuthControllerBase`** — email/password/childName/birthDate/
  doctorCode fields, Register button handler (moved from `OnRegister`, including the
  `AuthSession.Register` → `SetChildProfile` → optional `LinkByCode` → `GoToGame` sequence),
  link handler to Login.

- **`ForgotPasswordController : AuthControllerBase`** — email field only, Send Reset handler
  (moved from `OnForgotPassword`, calling `AuthSession.SendPasswordReset`), link handler to
  Login.

`AuthScreenController.cs` is deleted once the three replacements are wired up and verified.
`AuthSession` and `FirebaseAuthClient` are untouched — both are already flow-agnostic and
reusable as-is.

### 3. Scene builder tool

`WordFlowLoginSceneBuilder.cs` is refactored into shared layout helpers (canvas setup, field
creation, button creation, status text creation, link-text creation) plus three build
methods, exposed as menu items:

- `Tools > WordFlow > Build Login Scene`
- `Tools > WordFlow > Build Register Scene`
- `Tools > WordFlow > Build Forgot Password Scene`
- `Tools > WordFlow > Build All Auth Scenes` (convenience — calls all three)

Each remains idempotent (safe to re-run, rebuilds the scene from scratch), consistent with
the current builder's behavior.

### 4. Build settings

`Register.unity` and `ForgotPassword.unity` are added to `EditorBuildSettings.scenes`
alongside `Login.unity`, matching `Login.unity`'s current enabled/disabled state — so the set
of scenes actually included in a build stays consistent with today's configuration (no
unrelated build-settings changes).

## Testing / verification

- Build all three scenes via the new menu items; confirm each contains only its relevant
  fields/buttons.
- Manual flow test in the Unity Editor (per project convention — no automated Play Mode
  driver available due to Windows path-length limits noted in prior sessions):
  - Fresh account: Register → fills fields → lands on WorldMap.
  - Existing account: Login → lands on WorldMap.
  - Auto-login: relaunch Login scene with a stored session → skips form, auto-navigates.
  - Forgot Password: enter email → status text confirms reset email sent.
  - Cross-links: Login → Register → Login → Forgot Password → Login, confirm each scene
    loads correctly and fields are empty/fresh each time.
- Confirm `AuthScreenController.cs` has no remaining references after deletion (compiler
  will catch this).

## Open questions / risks

- None outstanding — Forgot Password requires no backend work (confirmed above), and no
  panel infrastructure needs to be built since this follows the existing scene-per-screen
  convention.
